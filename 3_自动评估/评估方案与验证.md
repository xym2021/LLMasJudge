# 评估方案与验证

## 1. 评分维度

评分由三部分组成：

- **Trip+ 原有的四层评估协议**：回应方式、行程可行性、需求满足与多轮状态、旅行者体验。前三层是规则代码，第四层是 LLM 评委（本方案称 Judge A）。
- **本方案扩展的 Judge B**：评价回复"说得"对不对，补上 Trip+ 规则看不到的交互行为。
- **人工复核**：处理证据不足、规则与原文矛盾、Judge 与人工分歧的情况。

来源：Trip+ 论文第 3 节与附录 B.1–B.7；评分代码在 `trip-plus/evaluation/`。

**Trip+ 原版如何汇总这些分数**（论文附录 B）：

- **回应方式、本轮更新落实、前序要求保留**：对所有轮次计算后取平均；
- **可行性、硬约束、软偏好**：只在"期望和实际都是出方案"的轮次上计算；
- **旅行者体验**：每个 case 只算最后一份方案。

本方案沿用这套口径报告 Trip+ 的分数，同时增加下面的逐轮判定。

### 1.2 每轮判定

- **合格**：【关键】【重要】全部通过；
- **基本合格**：【关键】全部通过，【重要】只有 1 项未通过；
- **不合格**：任一【关键】未通过。

Judge B 的 partial 在【重要】项上算未通过，在【关键】项（B1）上交人工复核。not_applicable 和 insufficient_evidence 不计入。

**关于边界轮的报告方式**：37 轮中出方案 27 轮，一个永远只出方案的模型，回应方式正确率也有 73%。所以回应方式要按类别单独报告：澄清轮的正确率、判无解轮的正确率，以及成对案例中"不该问"那两轮有没有多余反问。

**为什么 L4 不参与合格判定**：体验分是连续的主观分数，本方案只有 1 个评委，稳定性未经验证。先作为参考指标报告，验证稳定后再考虑设门槛。【偏好】

### 1.3 Judge B 补的是什么

Trip+ 的规则只检查回复里有没有 `<clarification>`、`<no_solution>` 标签，不看里面写了什么；行程规则也只检查行程本身，不看模型对用户说了什么。以下情况规则都会判"通过"：澄清时问了一串无关问题；判无解却说不清原因；悄悄替换了用户的条件；带老人孩子在酷暑出行却一句提醒都没有；声称"已为您预约"。Judge B 的 Prompt 见 `Judge_Prompt.md`。

## 2. 分工

**适合由 Judge 判断的**：需要读懂回复原文、结合语境判断的内容，即 B1–B4 和旅行者体验。这些没有唯一标准答案，但能在原文里找到证据，所以要求 Judge 逐字引用原文。

**必须用规则或工具结果判断的**：有确定答案、LLM 容易看走眼的内容。例如回应方式；选的是不是数据库里评分最高、最便宜、最近的那一个；车次和时间是否与工具结果一致；预算有没有算对；每天景点数、户外时长等数值条件。这些交给 Trip+ 的规则代码，并明确告诉 Judge **不要推翻规则结论**。

**必须由人工判断的**：见总表 H 行；此外还有沙箱之外的事实（例如 AI 产品回答中提到的真实票价，需要查官方来源），以及验证阶段所有样本的人工标注，这是评价 Judge 的基准。

## 3. 证据不足时如何处理

| 情况 | 处理 |
|---|---|
| Judge 缺少判断所需的输入（例如没提供工具证据却要判 B4） | 标 insufficient_evidence，列出缺什么；不计入得分；转人工 |
| 模型回复无法解析、规则评分缺失 | 该轮记为"评测失败"而不是"模型失败"；修复解析后重跑 |
| 规则结论与回复原文矛盾 | Judge 标 possible_rule_error；人工查看原文后决定是规则还是模型的问题，并记录 |
| 标注本身可能有误（例如标准答案依赖的数据库字段缺失） | 人工核对数据库；确认有误的轮次从统计中剔除，并在报告中说明 |
| 同一 case 两次运行结果不一致 | 两次都报告，不挑好的那次；只出现一次的失败不作为结论 |

## 4. 验证流程

### 4.1 设置

- **被测模型**（temperature 0，跑满 10 个 case；均尽量关闭思考）：
  - DeepSeek：`deepseek-flash`，DeepSeek 官方 API；
  - Kimi：`kimi-k3`，阿里云百炼；
  - 小红书：`dots3-note-prev`，小红书内部预览 API（结果目录名同模型 ID）。
- **Judge 模型**：千问。不评测千问本身，以避免给自己打高分；若后续也要测千问，Judge 改用另一家。
- **思考模式**：DeepSeek / Kimi 可关闭；`dots3-note-prev` 实测传了 `enable_thinking: false` 仍会返回少量 `reasoning_content`，无法完全关掉，记录为局限。
- **记录**：模型名、API 模型 ID、运行日期、temperature、是否开启思考，以及查不到的信息（写"未知"）。

### 4.2 预选的 6 个 case 及划分

| 用途 | Case | 选择理由 |
|---|---|---|
| 调试 | 0006 | 与画像冲突，应澄清，考 B1 |
| 调试 | 0029 | 缺信息，应澄清，考 B1；三代同堂遇酷暑，考 B3 |
| 调试 | 0005 | 5 轮走完出方案、澄清、判无解、再出方案，考 B1 判无解、B2 和前序保留 |
| 验证 | 0006P | 与 0006 成对，不该问，考回应方式和 B2 是否体现取舍 |
| 验证 | 0029P | 与 0029 成对，不该问，考回应方式；第 2 天晚餐和人均上限由 Judge B 或人工核对 |
| 验证 | 0148 | 澄清后判无解，考 B1 与"别偷换" |

- 调试样本和验证样本覆盖相同的维度（澄清、判无解、不该问、风险提示），但 case 不同，调试时改的 Prompt 不会"背答案"。
- 两组成对案例都拆在两边：原 case 在调试组，改编 case 在验证组。这样能检验调试时针对 B1 的修改能否推广到"不该问"的场景，而不是让 Judge 学会"见到这类话就判澄清正确"。

### 4.3 步骤

1. 用 DeepSeek、Kimi、小红书三个模型各跑完 10 个 case（人工与 Judge 的对比只用上面 6 个），保存 `trajectories/`、`reports/`、`evaluation/` 原始输出。
2. **人工先标注**：在看 Judge 结果之前，按 B1–B4 逐轮标 label 并写出依据。标注完成后锁定，不再修改。
3. 运行 Judge B（v1.0），逐轮对比人工结果。
4. **只在调试样本上**分析分歧、修改 Prompt，得到 v1.1。
5. 用 v1.1 在验证样本上跑一次，**不再修改**，报告一致率和分歧。
6. 如果验证样本上没有分歧，额外构造几条容易误判的回答做压力测试，并标注"人工构造，不计入模型表现"。候选例子：
   - 0148 T2：嘴上说"做不到"，却附了一份悄悄换了酒店的方案；
   - 0006P T1：用户已说明优先级，回复仍反问；
   - 某个方案轮写着"已为您预约好门票"；
   - 0029：为三代同堂写了大段防暑健康建议，却没给行程方案。
